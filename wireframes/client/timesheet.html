Where the action lives.
"Send allocation sheet" and "Download" sit on the Back Office event page (§11.4). The Client Portal only downloads the PDF (§11.1, §11.2) — no sending from the client side. No time restriction: the manager can send or download at any point, including mid-event (§11.3).
Recipients (§9.7, §11.4)
The 2–3 contact emails on the client card — several recipients per event (e.g. Dorchester → 3 people). Sender is always timesheets@thehospitalitycompany.co.uk; replies go to a monitored THC mailbox, never a no-reply (§9.12).
File name (§11.3)
Client name – Event name.pdf — pulled from the event build, e.g. "Leonardo Hotel St Pauls – Waiting M&E.pdf". The same name is used for both states; the sign-out copy is a later email with the same attachment name.
Behaviour notes. Format (§11.3): 1:1 with THC's current PDF timesheet — not our own design. ONE document per EVENT with all roles together, never one per role. Name: Client name – Event name (from the event build). Header: THC logo + name · STAFF ALLOCATION · Date DD/MM/YYYY; the PO Number from the event (§3.2) carries into the document. Columns: Photo (so the person can be matched on site) · Staff Name = Name (Employee ID) + (Role) — the Employee ID is the payroll identifier auto-generated when the candidate became compliant (§2.7) · Start Time = scheduled start + forecast finish in brackets · Finish Time = actual finish · Signature (by hand) · Comments (breaks etc., clients also write by hand, so the column stays) · Hours Worked. Footer: Total Hours · Manager's Name (PRINT) · Manager's Signature · Date + the company details (Registered Company 12411407, timesheets@thehospitalitycompany.co.uk, www.thehospitalitycompany.co.uk). · Pagination (§11.3): at most 12 staff rows per page; header block and column headers repeat on every page; every page is footed "Page X of Y"; every page after the first carries the event name and date again with "(continued)"; a staff row is never split; the footer block appears ONCE, on the final page, and Total Hours is the total for the whole event. Rows ordered by role section, then by surname within the role. · Two states (§11.3): (1) Allocation report — the blank form sent BEFORE the event, typically a day ahead but with no time restriction: assigned workers and their allotted hours; Finish · Signature · Comments · Hours empty for the client to fill in by hand on site. (2) Sign-out timesheet — generated AFTER the event: actual finish, breaks from the break log, hours worked and the calculated Total Hours populated from check-in/check-out; Signature stays empty in both — it is the client's, by hand. A worker whose shift still carries an unresolved "No check-out" violation (§9.5, RULE-02) gets blank Finish Time and Hours Worked cells rather than a guess; regenerating after the manager resolves it fills them from the manager-entered time. · Hours (§5.2, §5.2b): RULE-01 payable time = intersection of [check-in, check-out] with the scheduled window, so a 23:42 check-out on a 23:30 finish pays to 23:30; unpaid breaks are deducted where the client's break policy says "does not pay" (§3.2). Display as h m; the exact format is to be matched against THC's PDF. · Sending (§11.4, §9.12): "Send allocation sheet" (action) + "Download" (PDF, WhatsApp-able) + email, from the Back Office event page; several recipients from the client card (§9.7); sender timesheets@thehospitalitycompany.co.uk. · GDPR (§1.7): PDFs created and sent before a removal keep the worker's real name and photo exactly as issued — a historical record for billing/HMRC, never retroactively edited or reissued. Any copy regenerated or re-downloaded AFTER the removal uses "Deleted account #id" and no photo, the same as the live views. · Open points: the sign-out copy keeps the "STAFF ALLOCATION" title because the format is fixed 1:1 — confirm with THC whether the after-event copy should read "TIMESHEET"; a "Generated" stamp is deliberately NOT printed (not on the original form). No money on the document (§11.1).
