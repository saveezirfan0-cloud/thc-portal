Product summary (at a glance) 
The Hospitality Company platform is a bespoke system (THC owns the code, with IP transfer) that carries 
temporary staff for an event agency from application through to payment. Three applications around a single 
database: 
1. Back Office Portal (web) — the back office: onboarding, scheduling + auto-assign, compliance, check-in 
monitor, clients / venues / roles, reports, feedback. 
2. Staffing App (mobile, native Flutter iOS + Android) — the worker's app: onboarding, shifts, radar of open 
shifts, invites, check-in / check-out with background geofence, documents. 
3. Client Portal (web) — a restricted portal for the customer: their own events + line-up, with no rates or 
charges. 
Brand: one name and one logo across the whole system — "The Hospitality Company" + the "two glasses" logo 
in a cyan box. 
Visual system (Design System): deep navy background (#04080f), cyan accent (#3edcec), Space Grotesk 
(headings) / Inter (body) / IBM Plex Mono (labels), zero border-radius everywhere, square avatars. Components: 
Web/Sidebar, Web/Topbar, AppHeader (mobile), Web/Pill, Web/Button, SegToggle, Input, DocRow.

belong to.

1. GENERAL INFORMATION / CROSS-CUTTING 
1.1 Context and goal 
• 
Client: The Hospitality Company (London), an event-staffing agency, ~1,000 external workers on the books, 
10–15 events per day in season. 
• 
Goal: replace the old Accelerate system (awkward UI) with an in-house one — modern, fast, and built for a 
Gen-Z (18–30) audience. 
• 
Employment model: zero-hours (Uber-style). Workers are employed by THC (PAYE / payroll on the client's 
side). Onboarding → compliant → the worker receives shift invitations → accept / reject. 
• 
The code is transferred to THC in full. Hosting: the development environment sits with the supplier for the 
duration of the build; production — DigitalOcean or AWS, at THC's discretion. 
1.2 Three applications on a shared backend 
1. Back Office Portal (web, admin staff) — responsive; works on tablet and phone. 
2. Staffing App (mobile, native Flutter iOS + Android — critical for the background geofence). 
3. Client Portal (web, the customer — their own events + line-up, no money) — responsive in the same way as 
the Back Office Portal: it must work on phone and tablet, not desktop only. 
1.3 Technology stack (FIXED) 
• 
Backend: Django + DRF + PostgreSQL + PostGIS (geo: distances, geofence radii). Auth = DRF Token. 
• 
Web (Office + Client): React (Vite + React Router + axios) — the production stack from day one, nothing 
throwaway. 
• 
Staffing App: Flutter — one codebase, background geolocation via plugins (geolocator + 
flutter_background_geolocation). 
• 
Geo: address → geo point (reverse geocoding), home ↔ venue distance, geofence radius per venue. 
• 
Notifications: push (FCM / APNs, device-level) + SMS (via Willo).

1.5 Data model (key entities) 
• 
Role: name · description (internal, optional) · pay_rate (£/h base). Derived: final = pay × 1.1207 (holiday 
+12.07%, calculated, not stored). 
• 
Staff / Candidate: name · email · phone (international picker) · dob (all branches) · home_address + lat/lng · 
photo_url (selfie) · status (state machine, §2) · rating · reliability · roles[] (minimum age 18) · 
client_qualifications[] (which client + role combinations this worker is cleared for, §9.6) · left_at · 
leave_reason (both set when the worker leaves through the app, §10.6) · term_dates[] (the holiday ranges 
read from the verified University Term Dates Letter) · graduated_at (set when a completion letter is verified, 
§4.5) · wtr_optout (48h opt-out) · user (login). There is no stored weekly hours cap. The cap is a calculated 
value, derived from these fields on the date it is being evaluated (RULE-20, §4.4) — it is never typed in, 
never stored, and never edited by anyone. 
• 
Client: name · contact_name · email · phone · rate_cards[] · default_onsite_contact. 
• 
ClientRateCard: client · role · charge_rate (£/h, individual per client) · dress_code (predefined list + "Other" 
free text — set per client per role, since the same role can have a different dress code at different clients, 
confirmed by THC). 
• 
Venue: name · address · lat/lng · venue_type · geofence_radius_m (100–3000). 
• 
Event: client · venue · title · date · start/end · notes · dress_code (per role, from the list or Other) · 
onsite_contact (pre-filled from the client) · status (Upcoming / Ongoing / Completed / Cancelled — 
computed automatically from the event's start/end time, except Cancelled, which is set manually via the 
Cancel event action, §3.2) · shifts[]. The event's start/end is the event window — the earliest start and the 
latest end across its roles (§3.2). It is what the status calculation, the Client Portal and the calendar use; it is 
not itself the time any individual worker is booked for. 
• 
ShiftRequirement: event · role · start · end · headcount · buffer · charge_rate · pay_rate (filled counts ONLY 
confirmed). Start and end are held per role, not only on the event: a single event can carry a Chef section 
starting at 07:00 and a Waiting Staff section starting at 17:00, each with its own finish time (§3.2). Every 
scheduled-time rule in this document — RULE-01's pay window, the 30-minute check-in grace, the 15-
minute and 4-hour check-out windows, the day-before 12:00 cutoff, BG-01/BG-02 reminders — is evaluated 
against the role's start and end, because that is the shift the worker actually agreed to. 
• 
ClientQualification: client · role · staff · granted_by (manager, or "system") · granted_at · do_not_return 
(bool) · note (optional, internal). The qualification is held per client AND per role, not per client alone: a 
worker can be cleared as Waiting Staff at Client A and not at Client B, and can be cleared as Waiting Staff but 
not as Bar Staff at the same client. A row exists only where a worker is cleared; there is no "unqualified" 
record. This is what makes a worker part of the first-choice pool for that client's events (§3.4, §9.6, §9.7). 
• 
Booking: shift · staff · status · source (auto / manual / self) · created_at · confirmed_at · 
day_before_confirmed_at · on_day_confirmed_at. 
• 
CriminalDeclaration: staff · declared_at · source (onboarding / in-employment) · answer (yes / no) · details 
(free text, only where the answer is yes) · conviction_date (optional) · review_status (pending / verified / 
rejected) · reviewed_by · reviewed_at · review_note. A worker has a history of declarations, not one value: 
the onboarding answer is the first record and every later declaration made from the app (§10.7) is added 
alongside it. A declaration is never edited or overwritten once submitted — the record of what was 
declared, and when, is the point of it. 
• 
ComplianceDoc: staff · doc_type · expiry_date · review_status (pending / verified / rejected) · 
rejection_reason · share_code (value) + gov_report (PDF) + right_to_work_until · ai_confidence / 
needs_manual_review. 
• 
CheckLog: booking · check_in_at · check_out_at · on_site_verified · attempted_at (timestamp of every 
check-in button press, logged regardless of outcome — including attempts that are rejected, e.g. turned

1.7 GDPR / security / non-functional 
• 
Everything is notification-driven; the UI is fast, built for Gen-Z. 
• 
Age ≥ 18 — enforced on the form and on the backend. GDPR consent on /apply. 
• 
GDPR "Remove from system": double confirmation → irreversible anonymisation of personal data (name → 
"Deleted account #id", contacts / documents / photo wiped), login disabled, future bookings released, status 
Removed; history (bookings / feedback) is retained for reporting. 
• 
The removed worker's profile can still be opened by an admin (confirmed 28.07.2026): personal data 
(RTW/HMRC documents, bank details, contacts) is gone, while non-personal data — event history and 
feedback — remains visible, consistent with the "retained for reporting" rule above. 
• 
In the Staff directory's Removed tab, and anywhere a removed worker's row appears on a past or upcoming 
event they worked (Event board §3.3, Check-in monitor §9.5), the row is NOT filtered out — it stays, labelled 
"Deleted account #id", so the slot/headcount isn't skewed. Fields not tied to personal identity, such as roles 
and rating, can remain visible; the name and photo stay anonymised as above. 
• 
Already-generated Timesheet / Allocation Sheet PDFs (§11.3) that were created and sent before a GDPR 
removal request keep the worker's real name and photo exactly as issued — they are a historical record of 
what the client actually received, retained for billing/HMRC purposes, and are never retroactively edited or 
reissued. If a manager regenerates or re-downloads a timesheet or allocation sheet for a past event AFTER 
the worker has been removed, that new copy uses the anonymised "Deleted account #id" label and no 
photo, the same as the live views — confirmed 31.07.2026. 
• 
Feedback comments are free text and may name the worker directly (e.g. "[name] ran the floor 
brilliantly..."). Confirmed by THC: the worker's name should ideally be redacted from this text as part of 
anonymisation. Automatically detecting and redacting a name inside free text requires an LLM step and is 
not built in v1. The v1 behaviour is defined instead: on removal, feedback comments are retained verbatim 
and the office redacts a name by editing the entry (office feedback) or deleting it (client feedback, §9.10) if 
asked to. 
• 
TLS in transit, encryption at rest, role-based access.

1.8 Time zones — how times are displayed 
The client and every event are in the UK, so all times are stored and calculated in UK time (Europe/London). This 
section governs display only. It changes no rule anywhere in this document: RULE-01's pay window, the 12:00 
day-before cutoff, the 30-minute check-in and 15-minute check-out grace windows, and the 4-hour check-out 
limit are all evaluated in UK time regardless of where the person reading the screen happens to be. 
Why it needs stating: the office can be staffed from outside the UK, so the same screen may be read in a 
different zone from the one the event runs in. The rule for a SCHEDULED time is to show both zones, with the 
local line omitted when the two coincide — never a single unlabelled clock that the reader could mistake for 
their own. 
Check-in monitor (§9.5), WINDOW column: the scheduled shift window is shown on two lines — "06:15 – 23:00 
UK time" on the first, "08:15 – 01:00 your time" on the second. The second line is not rendered at all for a viewer 
already in UK time. The same dual display applies on the event card, in event details, in the Client Portal and in 
reports (client decision, 02.09.2026, recorded as ADR 0058). One deliberate exception to the dual-display rule: a 
status pill is too narrow to carry a zone label, so the "Due [scheduled start time]" pill on the same monitor (§9.5) 
shows the viewer's local time only, with no "UK time" / "your time" suffix. This is intentional and must not be 
"fixed" back to UK time — the WINDOW column in the same row already carries both zones, so the UK reference 
sits directly next to it on screen. If the underlying value carries no zone to convert from, the pill falls back to UK 
time, as before. Actual check-in and check-out stamps are treated differently from scheduled times and are 
shown in the viewer's local zone only, on a single line, never dual: they are real instants rather than an 
arrangement about the future, and keeping them in the same zone as the "Due" pill is what makes the lateness 
arithmetic on the monitor read correctly (e.g. Due 08:15 against 08:47 · GPS). This is settled, not pending — it 
should not be "aligned" with the dual display used for scheduled times. Input works the other way round from 
display: every field where a manager TYPES a time — the event form, and the actual-finish field when resolving a 
"No check-out" violation (§9.5) — is entered in UK time, because the server reads a zoneless value as 
Europe/London. Any such field must carry "(UK time)" in its own label, since the manager reads local times 
everywhere else on the same screen and would otherwise have no way to tell which zone is expected. A third 
category sits apart from both: audit records — the contract-signature timestamp (§2.11) and the document-
verification stamps beside it (§9.6) — are always shown in UK time and never converted, because they evidence 
when something was signed or approved and the hour must read identically to everyone who opens that file. So 
the real distinction is not "scheduled versus actual" but "operational versus audit": stamps a manager acts on 
today (Due, check-in, check-out) follow the viewer's zone, records of a decision already taken do not. 
2. ONBOARDING / ATS 
ATS = Applicant Tracking System — the entire journey of a person from application to becoming a member of 
Staff, in one pipeline. Here the ATS is the onboarding module of the Back Office Portal: public form → AI video 
interview (Willo) → Right to Work + documents → H&S quiz → contract signed → the candidate becomes Staff 
and leaves the pipeline. In parallel, the module performs compliance intake (collecting and verifying 
documents, gov.uk share-code checks, AI date extraction) — which is why "Onboarding" and "ATS" mean the 
same thing in this document.

from 18) + GDPR consent. 
• 
Under 18 → the application is rejected (checked both on the form and on the server).

2.3 Candidate profile /onboarding/:id 
• 
For EACH phase — only the relevant fields + the correct stepper (documents are not held on the early 
phases). Phase states: Interview requested · Interview completed · Documents · Quiz · Additional info · 
Contract (separate screens + states). 
• 
Documents come with two actions: Verify and Reject. There are no other top area buttons in the profile — 
only Reject candidate. Rejecting a candidate is final — there is no "un-reject" action on this record. If THC 
wants to reconsider them, the person applies again via /apply (§2.1), which creates a brand-new candidate 
record and runs the full onboarding process from scratch, the same as any other applicant. The Criminal 
Record declaration follows the same Verify/Reject mechanic only when the candidate answered Yes; a No 
answer is auto-verified on submission and never needs a manual action. 
• 
What happens when a document is rejected: the manager gives a reason → the document becomes 
Rejected → the worker receives a push: "Document rejected — [reason]" + a "Re-upload" button. They 
upload a new one and the document returns to review. 
• 
The move to the quiz is automatic: as soon as ALL documents — including the Criminal Record declaration — 
are verified, the candidate advances to the "Quiz" stage by themselves. A No Criminal Record answer is 
auto-verified on submission; a Yes answer needs the manager's manual Verify, same as a document. While 
anything remains unverified, the quiz stays locked. 
• 
Weekly hours limit — displayed, never edited. The profile shows the worker's cap for the current week and 
what produced it, e.g. "20 h/week — term time until 13.12.2026" or "48 h/week — university holiday until 
05.01.2027". There is no field to type a number into, for any worker, student or not: the cap follows 
automatically from the verified term dates (RULE-20, §4.4). What the manager verifies is the document and 
the dates read off it — the cap then takes care of itself. 
• 
Term dates (students): the AI reads the holiday ranges from the University Term Dates Letter and pre-fills 
them; the manager checks them against the letter and verifies, exactly as for any other document. These 
dates are the single input to the cap calculation — correcting a date here changes the worker's cap from that 
moment on, automatically, with nothing else to update. The manager confirms the dates, not the hours. All 
periods from the letter are shown — no cap on how many. A "+ Add period" control is needed next to the 
AI-extracted vacation ranges, so the manager can manually add a period the AI missed (e.g. a poorly 
scanned letter, non-standard format) — the manager should not be a hostage to OCR/recognition quality. The 
number of periods stays arbitrary (as already stated) — the "5" shown in the design is demo data, not a fixed 
constant. Real cases range from zero periods to three or four. 
• 
Share code: the applicant/worker enters the code themselves (and their DOB) on the registration page in the 
app (§2.5) — not the manager. Once entered, the system queries gov.uk itself, gets back the validity and the 
right-to-work expiry date, and stores the PDF report on the profile, visible here on the candidate's card. 
Nobody types the date by hand.

2.4 AI video interview — Willo (willo.video) 
• 
Pipeline: Applied → Interview requested → Interview completed → (Accept) Documents / (Reject). 
• 
How it works: the candidate submits the form → the system automatically creates them in Willo and Willo 
sends them the interview invitation. 
• 
The system tracks the status ITSELF (no manual updating, no periodic checking): the moment the candidate

• 
The manager makes the decision inside Willo (that is where the video is watched). The candidate profile

• 
Rejected in Willo → the system rejects automatically. Accepted → the candidate advances to "Documents" 
by themselves. The decision does not have to be repeated in the system. At this same point, the manager 
selects the candidate's qualified role type(s) on their profile (§9.6) — this is what makes them eligible for 
shifts of that role later. 
• 
Integration inputs supplied by THC before the onboarding sprint: Willo API key, interview key and the

configuration, never in the codebase, and the stage mapping is editable in Django Admin so a change to the 
Willo pipeline does not need a release. 
2.5 Right to Work — 5 branches 
The share code is entered manually in the mobile app (a field, not a file upload) — the system then checks it 
against gov.uk itself (§2.6). Date of birth is mandatory in every branch.Share code format (corrected 31.07.2026 
— the earlier "letters only" wording was wrong and should be disregarded wherever it appears in this 
document): exactly 9 alphanumeric characters (letters and numbers), starting with "W", e.g. W123AB4CD; case-
insensitive; spaces are ignored on input (people often paste it as three groups of three, e.g. "W12 3AB 4CD"); 
valid for ~90 days from generation; used together with DOB by the checking organisation (gov.uk) to run the 
check. The input field should validate against this format (9 alphanumeric characters starting with "W", case-
insensitive, spaces stripped) before submitting to gov.uk. 
1. UK / Irish citizen — passport (photo) OR birth certificate + a document showing the NI number. No share 
code. + 48h opt-out. 
2. EU/EEA settled / pre-settled — passport / ID (upload) + Share Code (input) + DOB + 48h opt-out. Pre-settled: 
expiry + reminders. 
3. Work visa — passport (upload) + Share Code (input) + visa type (dropdown) + expiry (date) + upload of the 
visa photo/PDF (the manager cross-checks the details against the document). 
4. International student — passport + Share Code (input) + University Term Dates Letter (upload), and — once 
they graduate — the Official University Completion Letter (upload, §4.5). Limit 20 h/week during term; 
outside term 48 h + opt-out; holidays = the dates from the term letter (expiry rule — see §4.2). The in-term 
limit is 20 h/week for every student-visa worker, whatever the course, and it follows automatically from the 
verified term dates (RULE-20, §4.4). Nobody sets the number. No separate student visa upload — the Share 
Code's gov.uk check already returns visa status, work conditions, and expiry, so a visa upload adds no 
compliance value on top of it (confirmed 04.09.2026). 
5. Dependant / other visa — passport + Share Code (input) + visa / status document (upload) + expiry. 
6. The mobile document screens cover each Right to Work branch and each document status. 
7. Accepted National Insurance evidence (branch 1, and any worker supplying an NI number): an NI card or 
letter, an HMRC or DWP letter showing the number, a P60, or a payslip from a previous employer showing 
the number. Any of these satisfies the requirement — the manager verifies that the number on the

2.6 AI integrations in onboarding 
This covers the agreed AI capabilities: reading dates off documents, recognising a student's term dates, and the 
automatic gov.uk share-code check. 
• 
Share code + DOB → gov.uk/view-right-to-work → right-to-work-until date → PDF report stored on the 
profile; that date becomes the expiry used for reminders. On failure or low confidence → flagged for 
"manual review". 
• 
The AI reads EVERY uploaded document and extracts the expiry date from it, and from the University Term 
Dates Letter it extracts terms and holidays. It writes those dates onto the profile automatically. 
• 
From the Official University Completion Letter (§4.5) the AI extracts the completion / award date and the 
awarding institution, and pre-fills them the same way; the letter still goes to a manager for verification like 
any other document. 
• 
The AI provider for all document extraction in v1 is Gemini (decided 17.07.2026). The integration is written 
behind a single provider interface so the model can be swapped without touching the onboarding or 
compliance flows. 
• 
  The final word belongs to a human. The AI does not verify a document. It only pre-fills the data and 
shows its confidence level; the manager checks and confirms manually. Where the AI is unsure, the 
document is flagged as "needs manual review".

2.8 HMRC New Starter Checklist — how the form works 
What it is. The mandatory HMRC form for a new employee. Without it the employer does not know which tax 
code to apply — and is not allowed to pay. Its data is exported into the New Starter report (§9.9). No P45 upload 
or parsing (decided 13.08.2026, not in scope). A P45 document type was considered for onboarding and 
deliberately rejected: the app does not accept, store or read a P45 file. Every worker completes the Starter 
Checklist in full, manually, even where they physically hold a P45 — if they have one, they read the equivalent 
figures off it and type them in. The reason is that the checklist is the form HMRC actually requires and it has to 
be complete and declared either way (see the Declaration tick-box below), so accepting a second document 
would add an upload, an AI extraction step, a review queue entry and a reconciliation problem without removing 
a single field from the form.

2.12 State machine (Staff.status) 
/apply → interview_requested → interview_completed → documents → quiz → contract → compliant; branch 
→ rejected (Willo reject / quiz failed 3×); compliant ⇄ blocked (expired document, automatically or manually; 
unblocked after verification); compliant → blocked (the worker declares a criminal conviction from the app, 
§10.7 — released the same way as any other block, by verification plus the full compliance re-check); compliant 
/ blocked → inactive (the worker leaves, through the app, §10.6); compliant → removed (GDPR, irreversible). 
Blocked, inactive and removed workers receive no invitations and are not in the scoring pool. 
inactive is the leaver state. It is reached only one way — the worker requests it themselves in the app (§10.6) — 
and is left only one way: a manager presses Reset to candidate (§9.6) and the person completes onboarding 
again on the same record. There is no "reactivate" that puts a leaver straight back to compliant, because their 
Right to Work, tax position and contract all have to be re-established before they can legally work again. Leaving 
is not a punishment and does not touch show-rate, rating or feedback. 
A worker who left and comes back goes through onboarding from scratch — the full wizard again, not a partial 
document recheck — but does so on their existing record, not as a second one (see Reset to candidate below). 
Full re-onboarding covers: application → Willo interview → Right to Work + all documents → HMRC New Starter 
Checklist (tax situation may have changed) → Criminal convictions (may have a new conviction since) → H&S 
quiz (again) → contract. 
Why the full wizard rather than a partial recheck: tax and criminal-record status may have changed since they 
left; the Willo interview lets THC re-assess presentation, which can be very different a year on; and a returning 
leaver is not entitled to skip steps every other applicant goes through. It also removes the need to build and 
maintain a separate "partial re-onboarding" path. 
The record is never deleted. It stays blocked until a manager decides what to do with it, so the person's 
historical show-rate, feedback and violations are all in front of them before they decide whether to take the 
person back. To work again, the person completes onboarding from zero on that same record. 
Returning workers keep one record — "Reset to candidate". 
A worker who comes back is re-onboarded on their existing record, not as a new one. A Reset to candidate 
action is available on a blocked or rejected profile in the Back Office (§9.6): the manager presses it, gives a 


===== PAGE 14 =====
14 
reason, and the profile returns to the start of the onboarding pipeline with the full wizard to complete again 
(§10.3). 
What a reset does, precisely: 
1. Status returns to `interview_requested` and the person re-enters the onboarding kanban (§2.2) as a 
candidate; a fresh Willo interview is sent as for any applicant (§2.4). 
2. The Employee ID is retained. One person keeps one Employee ID across every period of employment, so 
payroll and every historical timesheet continue to reconcile (§2.7, §9.9). 
3. Compliance evidence is cleared so nothing stale can satisfy the new check: every Right to Work and 
compliance document, the share-code result, the HMRC New Starter Checklist, the criminal-convictions 
declaration, the H&S quiz result and the signed contract are all marked superseded and must be supplied 
again. Superseded documents are retained, read-only, on the profile as the record of what was held during 
the previous period — they are not deleted and they are never used to satisfy the new compliance check. 
4. History is retained and stays visible: shift history, show-rate, rating, feedback and violations carry over, 
which is exactly what a manager needs in order to decide whether to take the person back. 
5. Bookings are unaffected because a blocked or rejected worker holds none; the worker cannot be invited or 
self-apply until they are compliant again (§4.4). 
To make this the only route back, the public application form (§2.1) performs a duplicate check on submission: 
email, and mobile number plus date of birth. A match against an existing record does not create a second 
candidate — the application is routed to the office as a "returning applicant" entry on the onboarding screen, 
naming the existing record, and the manager either presses Reset to candidate on it or rejects the application. 
The applicant sees the ordinary "check your inbox" confirmation either way; they are never told the reason a 
previous record was blocked. 
A GDPR-removed worker (§1.7) is the one exception: their personal data is gone and cannot be matched against, 
so they apply as a genuinely new candidate and receive a new Employee ID.

3.2 Creating / editing an event (Shift Builder) 
• 
Client → venue (address → geo point, type → radius) → date/time → roles: start + end (per role) + 
headcount + buffer + charge (from the client's rate card) + auto-assign allocation. 
• 
Multiple roles, each with its own hours. An event is built as a list of role sections and every section carries 
its own start and end time. The manager sets an event date and an overall start/end first; each role added to 
the event is pre-filled with that window and can then be changed independently — so one event can run 
Chefs 07:00–15:00, Kitchen Porters 09:00–17:00 and Waiting Staff 17:00–23:30 without being split into 
three events. The event's own window is then derived: the earliest role start to the latest role end (§1.5). 
This is what the calendar, the event list, the Client Portal (§11.1) and the Upcoming events block on the 
Dashboard (§9.1) display, and what drives the Upcoming / Ongoing / Completed status. 
• 
Adding a role after the event has been built pre-fills it with the current event window in the same way; 
editing a role's times updates the derived event window immediately, and changing a role's start or end 
triggers re-confirmation for the staff already booked on that role only (§3.5) — the other role sections are 
untouched and their workers are not asked to re-confirm. 
• 
Each role's times are shown wherever that role appears: on the role section header on the event board 
(§3.3), on the invitation and the shift card in the app (§10.4), in the WINDOW column of the check-in 
monitor (§9.5), and in the Start Time column of the allocation sheet / timesheet (§11.3). A worker is never 
shown the event window in place of their own role's hours. 
• 
Editing an existing event: every field above (venue, date/time, headcount, buffer, charge rate, dress code), 
as well as the PO Number, can be edited after the event is created, the same way as at creation time. 
• 
Editing is only allowed up to the event's start time. Once the event has started — and therefore for any past 
event — editing is locked. 
• 
*Editing headcount below the number of workers already confirmed does NOT auto-remove anyone; the 
manager decides manually who to withdraw (§3.3). 
• 
Buffer = an absolute number (not a %); displayed as "6 (+1)" (6 required by the client + 1 buffer), NOT the 
total "7". In the list / calendar, headcount reads "N (+buffer)". 
• 
Why the buffer exists: THC deliberately overbooks shifts because people turn up late or drop out on the day. 
The buffer is the insurance against same-day dropouts (which is why the on-the-day confirmation does not 
release the slot, §3.5). 
• 
Dress code per event: for each role, defaults to the dress code already set for this client + role combination 
on the client's Rate card (§9.7) + an "Other" → free text override available per event.

On-site contact: free text, pre-filled from the client profile, editable per event. Notes / specific instructions

3.4 Auto-Assign (a switch, default ON) 
• 
Auto-assign is a switch, default ON (replacing the manual "invite N" button, which has been removed). It can 
be turned off at event or role level — for example when the client asks for a specific person. 
• 
On creation: role → headcount + buffer + allocation (how many invites per hour), with the default = 
headcount + buffer, editable. 
• 
If it is ON: from the moment the event is created it adds allocation invites every hour, in descending score 
order; earlier invitations stay open (they are not pulled or rejected); it keeps adding until headcount + buffer 
is filled — buffer is part of the confirmation target, not the actual working headcount (§3.2, §5.2 RULE-15). 
Auto-assign runs per role section, against that role's own start and end times (§3.2), so a single event can be 
filling an early Chef section and a late Waiting Staff section at the same time, with different pools and 
different overlap arithmetic. 
• 
  Qualified staff are invited first (RULE-17). Each hourly round draws from two waves, in order: 
•

elsewhere, inside their weekly hours limit, not self-cancelled off this event). They are ranked by the 
normal §6 score and invited in that order. 
• 
Wave 2 — everyone else. Workers who qualify for the role in general (§9.6) but hold no qualification for 
this client + role combination. Because the qualification is per role, a worker who is a Wave 1 candidate 
for the Waiting Staff section of an event can be a Wave 2 candidate for the Bar Staff section of the same 
event. Auto-assign only reaches them once every eligible worker in Wave 1 has already been invited and

3.5 Three-stage confirmation (the anti-no-show core) 
The problem it solves: a worker can confirm a shift two weeks out — and forget all about it by the date. One 
confirmation is therefore not enough. 
1. Initial confirm — the worker accepts the invitation (possibly two weeks ahead). Invited → Confirmed. 
2. Day-before "I'm ready" — the ONLY hard deadline. 
• 
The day before, the worker must press "I'm ready" (push). 
• 
The deadline is 12:00 noon the day before. 
• 
Not pressed by 12:00 → the system automatically releases the slot, sends the worker a push confirming 
they've been removed (N6b, §8), and starts auto-assigning a replacement. 
• 
Why noon: any later and there is no time to find a replacement and get them to tomorrow's morning shift. 
3. On-the-day — attendance confirmation (WITHOUT automatic slot release). 
• 
On the day of the shift the worker gets one more push: "Confirm today's shift." 
• 
  This is a reminder, NOT a deadline. If they do not confirm, the slot is not released automatically: on the 
day itself, finding a replacement is unrealistic. 
• 
So why have it: it is an early warning for the office. Whoever has not confirmed is shown with the status 
"Not confirmed today" in the Check-in monitor (§9.5) — they can still check in normally, exactly like anyone 
else — and the manager still has time to react manually (call them, pull someone from the buffer), 
confirmed 31.07.2026. 
• 
Same-day dropouts are covered by the BUFFER (§3.2) — that is exactly why THC overbooks (people turn up 
late or vanish on the day). 
If the event time / date, venue address, or dress code changes → everyone booked must re-confirm (an 
"Awaiting" state, not a banner) + push, since these changes affect the worker's job on the day. This applies 
whether it's the start time or the end time that changes — either one triggers the same re-confirmation flow. 
The push (N11, §8) is a standard device-level notification (FCM/APNs, §1.3) and reaches the worker even if the 
Staffing App is closed. The card shows a "Time Changed" tag, a line stating what changed (e.g. "Start time moved

no re-confirmation is triggered for already-booked staff.

4.5 Graduation — the Official University Completion Letter 
The problem it solves. Today a student-visa worker is permanently cycled between 20 h/week in term and 48 
h/week out of term, off the dates in their University Term Dates Letter. When they actually graduate, the course 
is over and the term cycling is meaningless — but nothing in the system tells it that, so the worker stays capped 
at 20 hours every time the calendar says "term". 
What is built. A new document type, Official University Completion Letter, added to the same document model 
as every other compliance document (§4.4) — it is uploaded, sits as pending, is read by the AI, appears in the 
manager's "Needs review" queue (§4.1) with Verify / Reject, and a rejection sends the worker the standard push 
with the reason and a Re-upload button (§2.3, §8 N8). No new review mechanism is introduced. 
• 
Where it is uploaded. Not a wizard step — the worker graduates long after onboarding. It sits on the 
Documents tab of the app (§10.4) as an optional document available to any worker on the International 
student branch, and on the candidate / staff profile in the Back Office (§2.3, §9.6). 
• 
What it does when verified. Verification sets `graduated_at` on the worker, and from that date the cap 
calculation (RULE-20, §4.4) stops consulting their term dates and returns a flat 48 h/week, permanently. As 
everywhere else, nobody types a number — verifying the document is the whole action. The change is

cap are untouched, and the worker receives push N14 (§8) telling them their limit has changed. 
• 
It overrides the term-time cycle outright. Once a completion letter is verified, the University Term Dates 
Letter stops driving that worker's cap and stops generating expiry reminders (§4.2). The term dates are 
retained on the profile as history — they are evidence of what the cap was at the time a past shift was 
worked — but they no longer switch anything. The worker's profile shows "48 h/week — graduated, 
completion letter verified [date]" in place of the term-time cycle. 
• 
Above 48 hours. The completion letter unlocks 48 h; it does not unlock more. To work beyond 48 h the

4.3 Document expiry — the consequences (automatic) 
On the day a document expires, the system does the following by itself, with no manager involved: 
1. Moves the worker to blocked. 
2. Removes them from ALL future allocations (confirmed shifts) — those slots are released and go into auto-

3. Withdraws all of their open invitations — they disappear from their app.

5. Locks the app: the worker can still log in, but sees ONLY the "Documents" tab. Shifts, Radar and Invites are

with emphasis on the total earnings figure. Holiday pay is excluded and not shown here (consistent with §9.8

gated by the geofence (this previously contradicted the "forgot to check out" example below, where check-

shift instead raises a "No check-out" Violation that only a manager can resolve (RULE-02, §9.5, confirmed

message is shown, per the GPS states above.

5.2 Time rules for pay 
• 
RULE-01 pay-window: payable time = the intersection of [check-in, check-out] with the scheduled [start, 
end], where check-out is either the timestamp the worker actually recorded (in-radius press, or the last 
known on-site GPS time when pressed off-site) or, for a shift closed via the "No check-out" Violation (§9.5), 
the finish date and time the manager enters when resolving it. Arrived 13:30 for a 14:00 start → those 30 
minutes are NOT paid; left early → deducted. A 15-minute grace window applies symmetrically on check-
out: checking out up to 15 minutes after the scheduled end is still paid only up to the scheduled end time 
(e.g. checked out at 16:15 for a 16:00 finish → paid to 16:00 — mirrors the check-in side, where checking in 
during the 30-minute grace window is paid from the scheduled start, not the actual check-in time). Between 
15 minutes and 4 hours after the scheduled end, a late check-out still pays only up to the scheduled end and 
raises a red flag on the Check-in monitor (§9.5) so the manager can verify with the worker — it does not 
change the payable amount. If check-out is still not pressed 4 hours after the scheduled end, RULE-02 takes 
over instead of any default (confirmed 07.09.2026). 
• 
RULE-02 no check-out: the "No check-out" Violation (§9.5) is raised on either of two triggers. First, and the 
usual one: check-out has not been pressed at all 4 hours after the shift's scheduled end — the button locks 
and the violation is raised instead of defaulting to the scheduled finish. Second: check-out was pressed off-
site but background tracking gives no on-site time after check-in, so the only available finish time would be 
the check-in timestamp itself (§5.1) — the violation is raised immediately on that press, rather than 
recording a zero-length shift. The shift's payable time stays undetermined until a manager resolves that 
violation by entering the worker's actual finish date and time — that manager-entered time is then used as 
the check-out for RULE-01's pay-window calculation. There is no silent default for a shift that is never closed 
(confirmed 07.09.2026). 
• 
RULE-14 4-hour minimum: this rule applies only to a worker who actually checked in and worked the shift. If 
their payable time then comes out under 4 hours, they are paid a 4-hour minimum regardless of the actual 
hours worked — unless the shortfall is explained by a Violation against them. A logged "Left early" Violation 
(§9.5) always blocks the floor, resolved or not — the normal RULE-01 pay-window deduction applies instead, 
no minimum. A "No check-out" Violation (§9.5, RULE-02) blocks the floor only while it stays unresolved — 
the same RULE-01 deduction with no minimum applies for as long as the manager hasn't resolved it. Once a 
manager resolves a "No check-out" Violation via "Resolve", the shift is treated as satisfactorily closed for the 
worker: the 4-hour floor applies again (if the manager-entered finish time still comes out under 4 hours), 
and the violation stops counting against the worker's show-rate — mirroring the fact that Resolving it means 
the shift ended to the client's satisfaction (confirmed 08.09.2026). The floor never applies to someone who 
did not work the shift at all: a buffer turn-away is governed solely by RULE-15 below (a fixed 4 hours if they

27 
were on time, nothing if they were late — RULE-14 does not override that "nothing"), a No-show is paid 
nothing, and a cancelled or withdrawn booking is handled under §3.3, not here. 
• 
RULE-15 buffer turn-away pay: under a strict Buffer policy (§3.2), a worker whose check-in attempt is logged 
(CheckLog.attempted_at, §1.5) within the 30-minute grace window but is turned away because headcount is 
already filled is paid a fixed 4 hours — a flat amount, not tied to the shift's scheduled length and not half the 
shift, since they never actually worked. A worker turned away who was themselves late is paid nothing for 
that shift. 
5.2b Breaks 
• 
Governed by the client's break policy (§3.2). If the client pays for breaks, the worker logs nothing — there 
are no buttons. 
• 
If the client does NOT pay, a breaks block appears on the shift screen in the worker's app. For shifts longer 
than 6 hours, this block also shows a banner/label: "A break will be applied to all shifts over 6 hours — 
please check with your Manager on site" (confirmed 01.09.2026) — this is informational copy only, 
referencing UK law (a mandatory 20-minute break for shifts over 6 hours); the system does not enforce or 
validate that any particular break length is actually taken. 
• 
Start break — available ONLY after check-in (you cannot be on a break you never started a shift for). Before 
check-in the button is disabled, with the hint "Unlocks after check-in". The Breaks block then stays available 
for the rest of the shift, right through until the worker actually checks out — it is not tied to the shift's 
scheduled end time and does not disable or disappear if the shift runs longer than planned (confirmed 
01.09.2026). 
• 
"On break" state: the break timer runs, the chargeable timer is paused, and the button becomes "Finish 
break — back to work". 
• 
6-hour break alert (added 02.09.2026). Where the client does NOT pay for breaks, a worker who has been 
checked in for 6 hours with no break logged receives a push: "You've been on shift 6 hours — please ask 
your manager on site about taking your break." (§8, N13). It fires once per shift, is skipped entirely if any 
break has already been started, and is informational — it prompts the worker, it does not create a Violation, 
pause the chargeable timer or enforce a break. 
• 
Scope note on the alert: this is not a by-product of the Breaks column on the check-in monitor (§9.5). That 
column is cheap because it renders data the system already stores, on page load. A push needs its own 
scheduled job, continuously checking every in-progress shift for "6 hours since check-in, no break logged 
yet" and firing at that moment — the same shape of background work as the check-in and check-out 
reminders (§7, BG-01 / BG-02 / BG-03). It is specified and estimated as its own item, BG-10. 
• 
Several breaks per shift are allowed. 
• 
The total break time is deducted from the hours worked → affecting both pay and charge. 
• 
Breaks appear in the Comments column of the sign-out timesheet (§11.3).

10.6 Leaving — "Request my P45" 
Why it exists. A zero-hours workforce turns over constantly, and until now there was no way for a worker to say 
they were finished. People simply stopped accepting shifts, stayed in the scoring pool, kept receiving invitations, 
and — worst of all — stayed sitting on confirmed bookings for events weeks away that nobody knew were going 
to be a no-show. This gives the worker a clean exit and gives the office the earliest possible warning. 
Where it is. A Request my P45 action at the bottom of the profile sheet in the app (§10.1), below the sign-out 
link, set apart from the everyday links and not styled as a primary action. 
What the worker sees. Tapping it opens a confirmation sheet headed "Leaving The Hospitality Company?", 
which states plainly and in full what will happen: their P45 will be requested from the office, they will be taken 
off every shift they are booked on, and they will not be able to book or be invited to shifts again unless they re-
apply. It carries an optional free-text "Reason for leaving" field, a Cancel and a confirm button reading "Yes, 
request my P45". The confirm button is deliberately not the default-styled action, and a second short "Are you 
sure? This can't be undone from the app" step sits behind it, so this cannot be triggered by a stray tap. 
What the system does, the moment it is confirmed: 
1. Status → inactive (§2.12), with `left_at` and the reason recorded on the profile (§1.5). 
2. Every future booking is released. All of the worker's confirmed bookings whose shift has not yet started are 
cancelled, the slots reopen on the event board (§3.3) and auto-assign begins back-filling them immediately 
(§3.4) — exactly as it does for any other released slot. 
3. A shift already under way is not touched. If a shift has started, or the worker is checked in, that booking 
stands and is paid and billed normally — the release applies only to shifts with a start time in the future, so 
leaving can never disturb the pay or the timesheet for work already being done. A worker who is checked in 
cannot submit the request at all: the action is disabled for the duration of that shift, with the hint "Available 
once you've checked out". 
4. Open invitations are withdrawn and any pending Radar self-application is cancelled, so nothing of theirs is 
left sitting on a manager's event board. 
5. They leave the scoring pool (§6) and cannot be invited, auto-assigned or manually added to any event. 
6. Email E8 goes to admin@thehospitalitycompany.co.uk (§8) — immediately, not batched. Subject: "P45 
requested — [name], Employee ID [id]". The body carries the worker's name, Employee ID, NI number, the 
date and time of the request, the reason they gave if any, the date of their last completed shift, and a list of 
the future shifts that were just released with the event, client, venue, role and date of each — so whoever 
picks it up can see instantly whether a big event has just lost someone as well as action the P45. 
7. The app locks to a leaver screen: "You've left The Hospitality Company. Your P45 has been requested and 
the office will be in touch. If this was a mistake, please contact us at: admin@thehospitalitycompany.co.uk."

Shifts, Radar, Invites and Documents are all closed; the worker can still sign in and still reach Payment

What it does not do. The system does not produce the P45 itself. A P45 is issued by payroll, and for the same

10.7 Declaring a criminal conviction while working 
Why it exists. The convictions question is asked once, at onboarding, and then never again — so a worker 
convicted of something in their second year has no way to tell THC other than a phone call that may never get 
recorded. The contract obliges them to disclose (§2.11); this is the route that makes that possible, and it 
produces a dated, auditable record rather than a note in someone's inbox. 
Where it is. A Declare a criminal conviction action at the bottom of the Documents tab (§10.4), below the 
document list — the same screen the original declaration was made on during onboarding (§10.3, step 4/11), so 
it is where a worker would think to look. Available to any compliant worker at any time. 
What the worker sees. A short form: a required free-text details field, an optional date of conviction, and a 
plainly-worded notice above the submit button stating what will happen — that their upcoming shifts will be 
paused while the office reviews the declaration, that the office will be in touch, and that declaring is a 
requirement of their agreement, not something they are being penalised for. Submit is followed by a 
confirmation step, because the consequences are real. 
What the system does on submission: 
1. A CriminalDeclaration record is created (§1.5), `source = in-employment`, pending review. Nothing already 
on the profile is altered — this is added to the history. 
2. The worker is suspended immediately, exactly as an expired document suspends them (§4.3): status → 
blocked, with the internal block reason "Criminal conviction declared — under review". 
3. Every future booking is released and goes back into auto-assign for a replacement (§3.4); open invitations 
are withdrawn and any pending Radar application is cancelled; they leave the scoring pool (§6). 
4. A shift already under way is not disturbed. As with leaving (§10.6), the release applies only to shifts with a 
start time in the future, so a declaration made mid-shift cannot upset that day's pay or timesheet. 
5. The app locks to the Documents tab, with copy that is factual rather than punitive: "Thanks for telling us. 
We've paused your upcoming shifts while the office reviews your declaration, and we'll be in touch. If you 
need to speak to someone, contact us at: admin@thehospitalitycompany.co.uk." The details the worker 
typed are never displayed back to them on a shared screen, and never appear anywhere in the Client Portal. 
6. Email E9 goes to admin@thehospitalitycompany.co.uk (§8) immediately — not batched, and not carrying 
the declaration text itself. It names the worker and Employee ID, the time of the declaration, and the future 
shifts that were just released with event, client, venue, role and date, so the office can see the operational 
hole at the same moment it learns of the declaration. The details are read in the Back Office, where access is 
role-controlled.

ongoing duty written into the contract (§2.11). On submission 
they are suspended like any expired document: future 
bookings released, invitations withdrawn, app locked to 
Documents, and E9 emails the office without carrying the 
details. A manager verifies (unblock via the full compliance re-
check) or rejects (becomes a manual block) 
Leaving 
The worker leaves from the app — "Request my P45" — 
status becomes inactive, every future booking is released to 
auto-assign, open invitations are withdrawn, a shift already 
under way is untouched, and E8 emails 
admin@thehospitalitycompany.co.uk with the released shifts 
listed. The system does not generate the P45; payroll issues it 
(§10.6) 
Returning workers 
Re-onboarded on their existing record via Reset to candidate
