# ADR-0091 · The New Starter (HMRC) report is emailed to Payroll and Gisela every Monday, on its own

**Status:** Accepted (THC, 05.10.2026). Agreed deviation from scope v1.6 §9.9, which sent the New Starter (HMRC) CSV only as a second attachment to the weekly payroll email. **§9.9, §7 (BG-08)**

## Context

§9.9 sends one email to the finance team every Monday at 09:00, "with 1–2 CSVs: Payroll — always; New Starter (HMRC) — only if there were new starters". On 02.10.2026 the owner paused that email (ADR-0083) because it reached the payroll provider while the platform was not carrying real shifts. Because the New Starter report was an attachment to it, pausing the payroll email stopped the New Starter report too: the job was never prepared, so no new starter reached Payroll. THC: "The New Starter Checklist report should be emailed to Payroll and Gisela every Monday."

## Decision

1. **Its own email, NS1.** From `admin@`, to the same two addresses as the payroll email (`thc_payroll@topsourceworldwide.com` and `gisela@thehospitalitycompany.co.uk`, read from E5, not retyped). One CSV attached, in the §9.9 Tab 3 columns. It goes **every Monday from 09:00 UK**, and a Monday missed by an outage is caught up later in the week. NS1 has its own switch in /settings → Notifications (ADR-0083), **on by default**, independent of BG08.
2. **BG08 no longer carries it.** The payroll email is the payroll CSV only, and its text says the New Starter report comes in its own email. `prepare_finance_reports()` no longer creates a New Starter send, `queue_finance_report_email()` takes the payroll file only, and `new_starter_export_rows()`, which read the payroll run, is dropped. Without this, turning BG08 back on would send the same people twice. A BG08 email queued before this change still reads as it was written.
3. **Who is in it** (the §9.9 Tab 3 rule, now independent of payroll):
   - a worker whose **first shift is settled**: they turned up, and the shift is not waiting on an unresolved "No check-out" (RULE-02). A first shift that is held waits, and the person goes out the Monday after it is resolved, exactly as the rule worked when it was tied to the payroll run;
   - **not sent before.** `new_starter_reported` is the ledger, one row per worker, written when a week is prepared and tied to its send. Nobody is ever sent twice, and a missed week is caught up;
   - first shift **on or after `settings.new_starter_report.not_before`**, so switching it on never reports every existing worker. It starts at the Monday before the migration ran. The ledger is seeded from the weeks BG08 had already sent.
4. **A week with nobody new sends no email.** It is recorded as "no new" and /reports reads "No new: [date], [time]", not a failure (§9.9, confirmed by THC 28.07.2026). This is the existing rule for the New Starter report. If THC wants an email every Monday even when there is nobody new, say so and it is one condition.
5. **The job** is `POST /api/jobs/new-starter-report`, a Back Office Node route like event-documents (ADR-0074), called by pg_cron every 15 minutes with the same bearer secret (`RTW_JOB_SECRET`, the vault's `office_base_url`). `new_starter_report_due()` picks the UK minute and respects the switch. Each step (prepare, rows, upload, queue) is idempotent, and the outbox key `NS1:<week start>` is unique, so a week is never emailed twice. The send status on /reports follows the outbox as it does for BG08.

## Consequences

- `20261005140400_new_starter_report_own_email.sql` (the ledger, the setting, four functions, BG08's two functions restated, the `job_schedules` row `new-starter-report`). pgTAP: `410_reports_payroll.sql` holds the new starters across a held first shift, and `190_job_function_grants.sql` the grants and the schedule.
- `apps/office/app/api/jobs/new-starter-report/` and its tests; `middleware.ts` lets the path through for POST with the bearer secret, as for the other two jobs. `supabase/functions/finance-reports` loses its New Starter step.
- `packages/notifications`: the NS1 email in `documents.ts`, its switch in `switches.ts`, its row in the office Inbox.
- **Deploy order.** The migration drops `queue_finance_report_email(bigint, text, text)` and `new_starter_export_rows(bigint)`, which the previously deployed `finance-reports` Edge Function calls. Redeploy `finance-reports` (`supabase functions deploy finance-reports`) with the migration. The payroll email is off today, so nothing breaks in between, but an old function would fail the first time BG08 is switched on.
- **Retry send** on a failed New Starter send re-queues the New Starter email (NS1), not the payroll one: `retry_finance_report()` takes its template and key prefix from the send's kind. A switch turned off after the email was queued settles it as failed (ADR-0083), and the workers are already recorded in the ledger, so Retry is the way to send them.
- **Stale rows from the old flow.** The old BG08 stamped a New Starter row for a week before its email was queued. On migration, a stamped-but-never-queued row is removed, and the cut-in date reaches back to the earliest week whose New Starter attachment never went (stamped, or queued and failed), so those workers are reported by the first run and not lost. `prepare_new_starter_report()` also replaces a "preparing" row that has nobody recorded against it.
- **Decision for the owner: it ships ON.** NS1 is on by default and its job is enabled, as THC asked ("every Monday"). The report carries NI numbers, dates of birth and home addresses to the payroll provider. The first Monday after `install_job_schedules()` sends everyone whose first shift settled since the cut-in date, **including test or demo workers on the target database**. To hold it until go-live, switch NS1 off in /settings → Notifications (or `update settings set value = value || '{"NS1": false}' where key = 'notification_switches'`) before running `install_job_schedules()`, then switch it on when real shifts are flowing, as was done for the payroll email (ADR-0083). The same applies to E5b (ADR-0092), which sends only when bank details change outside the app.
- **To go live:** deploy, then run `select install_job_schedules();` (docs/16 §4.7) so the new row reaches pg_cron. The two vault secrets `office_base_url` and `rtw_job_secret` already exist wherever event-documents runs. Nothing else is needed.
- The manual New Starter tab and Export CSV on /reports are unchanged.
