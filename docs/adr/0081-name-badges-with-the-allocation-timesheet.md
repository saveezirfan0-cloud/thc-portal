# ADR-0081 · THC name badges go with the Allocation Timesheet, for the clients that want them

**Status:** Accepted, 02.10.2026 (THC) · **Builds on:** [ADR-0074](0074-allocation-timesheet-autosend.md) (the Allocation Timesheet and its automatic send), [ADR-0073](0073-branded-html-email.md) (the D1 email), [ADR-0060](0060-viewer-role-two-step-reset-activation-links.md) (the viewer writes nothing), [ADR-0026](0026-client-reads-only-through-views.md) (the client role holds no table policy) · **§9.7, §11.3, §11.4** · **Code:** migration `20261002112000_client_name_badges.sql`; pgTAP `769`; `packages/pdf/src/badges.ts`, `BadgesDocument.tsx`, `lockup.ts` (generated by `scripts/gen-lockup.mjs`); `apps/office/app/api/documents/_lib/generate.ts`, `api/documents/[eventId]/badges/route.ts`; `apps/office/app/clients/[id]/NameBadges.tsx`; `events/[id]/_components/DocumentActions.tsx`; `packages/notifications/src/documents.ts` (D1)

## Context

THC asked on 02.10.2026:

> A certain client, Leonardo Hotel St Paul's M and E, requires THC name badges sent over when the staff timesheet is sent over. This is just a name badge with the THC logo at the top. These are then printed by the client and added into name badges. Can this please be added for Leonardo Hotel St Paul's M and E, so the name badge template and staff timesheet are sent across together.

The scope has no name badges. The nearest thing is §11.3's Allocation Timesheet. It is drawn per event from the confirmed line-up and emailed to the client card's contact emails (§11.4). Since ADR-0074 it is also sent automatically the day before at 14:00.

## Decision

### 1 · A switch per client, on the client card

`clients.name_badges boolean not null default false`. The client card's General info block has a **Name badges** switch (`set_client_name_badges`, audited as `client.name_badges` on the client's History). A viewer sees the state as text, not a control. The database refuses a viewer anyway (ADR-0060).

It is a switch on the client rather than code for one client because the next client to ask needs no developer. It is not on the New/Edit client dialog, because §9.7 makes every field there mandatory. A new client simply starts with badges off.

The migration switches it on for **Leonardo Hotel St Paul's M and E**. It matches the name with the spaces and punctuation taken out, so "St Paul's", "St Paul’s", "M and E" and "M&E" all match. It reports the count as a notice. If the card is named differently, the switch does the same job.

### 2 · The badges travel with the Allocation Timesheet (D1) only

Whenever `generateDocument()` draws an **Allocation Timesheet** for a client with badges on, it also draws the badges. That covers the Send button, the Download button and the automatic 14:00 send. It stores them in the `timesheets` bucket beside the sheet (`<event>/badges/<stamp>.pdf`). It then attaches them to the same `event_documents` row through `attach_event_document_badges()`, **before** the email is queued. Both queue paths build their payload through `event_document_email_payload()`, so the badges become the D1 email's second attachment with no change to either queue function.

The **Completed Allocation Timesheet (D2)** never carries badges. It goes the morning after the event, when a badge is no use.

Rules held in the database (pgTAP 769):

- Badges attach only to an `allocation` copy, and only for a client with the switch on. A table check holds the first rule too.
- Once a copy's email is queued, nothing can be attached to it (`document_already_queued`). What the client was sent is never changed.
- A copy carries one set (`badges_already_attached`), under its own event's folder, with at least one badge.
- Callers: the office (`assert_reports_caller`) or the service role (the job). Not anon, a worker or a client.

If the badges cannot be drawn, stored or attached, a **Send** (manual or automatic) stops. It does not email the sheet without the badges the client asked for. The job releases its claim and retries on the next run (ADR-0074). A **Download** never loses the sheet over the badges: it hands the manager the sheet, and records it, without them.

**What a failure leaves behind.** Recording the copy and attaching the badges are two calls. If the attach fails, an unsent copy of the sheet stays in `event_documents` and its files stay in the bucket. That is the same as a Download, which records every copy it hands out, and the Client Portal already lists the latest copy whether it was emailed or not (§11.3, 20260923130100). So nothing new is shown that the portal would not show after a Download.

**A failure that does not clear.** If the badges keep failing (a Storage fault, say), the automatic D1 retries up to eight times and then gives up (`gave_up`, ADR-0074). The manual Send fails the same way, so the client gets no Allocation Timesheet until the fault is fixed. That is deliberate: THC asked for the two together. If the office needs the sheet out regardless, switching Name badges off on the client card and pressing Send sends the sheet alone.

### 3 · What a badge is

- **86 × 54 mm**, the standard card size most badge holders take. Ten to an A4 page, two across and five down, centred. Dashed cut lines are shared between neighbours, so one cut serves two badges.
- **The THC stacked lockup** (glasses above "The Hospitality Company") at the top, 25 mm tall. It is drawn as vectors from `brand/thc-lockup.svg` (`lockup.ts` is generated, never hand-edited), in ink, so it prints the same in black and white.
- **The first name** under it, in bold. The size steps down for a long name so it stays on one line. A person with no first name on record gets the name the sheet prints. The surname stays on the timesheet: a badge is worn in front of guests, and the client already has the full name on the sheet.
- **One badge per person on the sheet, in the sheet's order**, so they come off the printer in the order the timesheet lists them. A worker removed under §1.7 gets no badge.
- No money, no Employee ID, no role, no photo.

The file is "Client – Event – Name Badges.pdf".

### 4 · The email and the event page

- D1's text and HTML gain one sentence after the PO line, only when badges are attached: *"Their THC name badges are attached too, as a second PDF: print them, cut along the dashed lines and slide each one into a badge holder."* It is singular for one badge.
- The facts box gains a **Name badges** row with the count. With no badges the row drops, as every empty fact does.
- The badges' file card reads "Name badges · N to print". The outbox row marks that attachment `role: 'badges'`, and the words come from D1's `badgesNote` in `packages/notifications`, never from SQL. The sheet's card keeps "Allocation Timesheet · attached".
- An outbox row from before this change still renders: no `nameBadges` means no sentence and no row.
- The event page shows **Download Name Badges** beside the Allocation Timesheet buttons for a badge client (`/api/documents/:eventId/badges`, drawn fresh, not stored). The Send confirmation says the badges go in the same email, and the result says how many.

### 5 · Nothing reaches the client role

The client role holds no table policy (ADR-0026). `client_event_documents_v` names its columns, so it does not gain the badge columns, and no `client_*` view exposes the switch. pgTAP 769 checks all three. The Client Portal's document page is unchanged. The client gets the badges by email only.

## Not in the wireframe

The client card wireframe now shows the switch. The event page's **Download Name Badges** button is not drawn in `backoffice/event-board.html`; this ADR is the deviation record.

## Consequences

- One more PDF is drawn per Allocation Timesheet, for badge clients only. Ten badges a page, vectors only, so it is well under a second.
- The `timesheets` bucket keeps every set of badges sent, like every sheet (§1.7: already-issued PDFs are kept).
- **To change for a client:** the switch on its card. **To change the size or layout:** `BADGE_SIZE_MM` and `BADGE_COLUMNS`/`BADGE_ROWS` in `packages/pdf/src/badges.ts`. The page centring follows them. **To change the logo:** regenerate `lockup.ts` from the brand file.
