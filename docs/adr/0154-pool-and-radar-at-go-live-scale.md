# ADR-0154 · The auto-assign pool and Radar at go-live scale

**Status:** Accepted · **Refines:** ADR-0117 (the pool is the one place gates are decided; one-worker readers read one row), 20261017180000 (the 17.10 Radar hotfix) · **Date:** 18.10.2026

## Context
On 17.10.2026 `staff_open_shifts()` (Radar, also behind /shifts' Open tab and /radar/[id]) took the live project down: it ran the auto-assign pool over the whole agency once per open section. The hotfix (20261017180000, applied live) read the viewer's own row instead, but two costs that grow with the agency were left, and the pool itself had the same shape for every list reader — the event board once per section every 30 s, the hourly / cutoff / escalation rounds once per due section, `offer_candidates`.

Reproduced at go-live size with `scripts/bench/radar_and_pool_at_scale.sql`: 1,000 workers, 600 open sections over 200 events, ~34,000 bookings (≈30 worked shifts each), client qualifications for about a third of each worker's (client, role) pairs. Local PostgreSQL 16, warm, same seed before and after; hosted Micro compute is slower.

| | before (main + 20261017180000) | after |
|---|---|---|
| Radar, worker holding all six roles, qualified everywhere (512 cards) | 3.9 s | 1.7 s |
| Radar, two roles, qualified at one client (13 cards) | **69 s** | 1.3 s |
| Radar, new starter, one role, qualified nowhere (0 cards) | **22 s** | 0.52 s |
| /radar/[id] | the whole Radar | 4.8–10.5 ms |
| Board, per section (admin, the board's filter) | 3.10 s | 0.20 s |
| Board, a multi-day job's section (admin) | 3.48 s | 0.25 s |
| Rounds, `auto_assign_candidates` per section (service_role) | 1.48 s | 0.12 s |
| Escalation round, per section | 1.48 s | 0.12 s |
| One worker's gate (`auto_assign_worker_gate`: invite, Accept, apply, take) | 7.6 ms | 4.2 ms |

Before, per worker in the pool: `weekly_cap_would_breach()` ~2.7 ms (its chain is parsed and planned again on every call when nested); `staff_show_rate()` over the whole history ~0.25 ms; booked-elsewhere over every confirmed or worked booking the worker ever had ~0.26 ms; the venue count ~0.17 ms — for wrong-role workers too. Radar asked the pool about every open section (wrong-role ones included) and, for each section the viewer is not qualified at, judged every qualified worker for RULE-17.

## Decision
Every gate, its order and code, the wave and the five score inputs are unchanged; pgTAP 854 compares each reader with its old body (see Consequences).

1. **The pool works out each fact once per call** (20261018140000). Show-rate (`staff_show_rate()`'s sample and formula), confirmed shifts to come, shifts at the venue, the hours in the section's Mon–Sun week (`booking_counts_toward_cap()` still says what counts), who self-cancelled off the event and who holds a confirmed or worked booking near the section are grouped joins, not per-worker subqueries. The RULE-20 verdict is `rota_guard_verdict()`'s, built from its own pieces (`weekly_cap_for()`, `can_roster_staff()` on the start and end day, `rota_guard_decide()`, `rota_guard_mode()`), asked only of a worker every earlier gate let through, as the CASE always did. The cap helpers are called as they are; their own cost is the parallel RULE-20 work.
2. **Booked elsewhere reads only the sections within the gap of this one.** A section ending before this one starts less the gap, or starting after it ends plus the gap, can neither intersect it nor sit too close to it (min_4h keeps every end after its start; a negative or missing gap only ever flags an overlap), so the window drops nothing `booked_elsewhere_conflict()` — still the judge — would flag. `shift_requirements(ends_at)` is indexed for it (and for Radar's "not over yet").
3. **Two branches per source, one runs.** A list call reads the agency's rows; a call for named workers (`p_only`) reads only theirs through the staff_id indexes, so a one-worker gate never aggregates the agency's history. The split is a one-time filter on `p_only`; what is done with the rows is written once.
4. **plpgsql with a session-cached generic plan, jit off.** A SQL function is parsed and planned again whenever another function calls it, which is how every one-worker reader reaches the pool. The body's estimated cost is far above `jit_above_cost`; compiling it cost seconds a call while running it costs milliseconds, so `jit = off` is set on the pool, on `auto_assign_candidates()` and on `staff_open_shifts()`.
5. **Stable order.** The pool and `auto_assign_candidates()` return rows by `staff_id`, so a reader that pages (the rounds and `offer_candidates`, where another session is adding paging) sees a stable order. Radar's ORDER BY ends on the section id, so ties no longer swap between loads.
6. **Radar asks the pool only about sections it could show** (20261018140100, re-created from the live body with targeted replacements). A prefilter keeps the worker's own pending application (until RULE-16 ends it) and otherwise only sections not started, with a slot left (confirmed + worked < headcount, `shift_fill()`'s count) and in a role the worker holds. Each test is one the query makes again; nothing is decided there, and the pool still decides every gate.
7. **RULE-17 stops at the first reachable qualified worker.** A qualified worker who already holds a booking on the section, lacks the role or is not compliant cannot be reachable (the pool's `booking_status`, `wrong_role`, `blocked`), so the pool is not asked about them; it is asked about the rest one at a time, inside an `EXISTS`. The cheap candidates sit behind `OFFSET 0`: written as one join, the planner sometimes (after a test run had churned the tables' statistics) put the pool call on a hash join's build side, asking it about every qualified worker before the first answer — 44 s for the two-role worker instead of 1.3 s.
8. **The week meter once per day.** Each card's booked hours and cap (`weekly_booked_hours()`, `weekly_cap_hours()` for the section's week) are asked once per UK day the candidate sections start on — the same functions with the same arguments — instead of once per card: 0.7 s of a 512-card Radar.
9. **`staff_open_shifts(p_staff, p_shift)`.** The optional second argument narrows Radar to one section, the way `staff_open_offers(p_offer)` does; `findOpenShift()` uses it instead of reading the whole list. The one-argument function is dropped (two would make a call with no arguments ambiguous); grants, SECURITY DEFINER and the comment are carried over.

### Owner rights: weighed, not taken
Running the pool SECURITY DEFINER would stop RLS being re-evaluated inside it for the board's admin. It was not done:
- The pool is reached from SECURITY DEFINER functions inside **staff** sessions — `staff_open_shifts`, `accept_invite`, `apply_to_shift`, `take_offered_shift`, `staff_open_offers`, `notify_offer_candidates` — so a definer pool cannot tell those calls from a worker calling it directly. The explicit guard `auto_assign_unavailable()` uses (admin, service_role or no JWT) would refuse them; no guard would let a worker read every worker's gates, distance and rating. Today a worker or client calling it directly reads nothing, because `shift_requirements` and `events` are office-only (854 F holds that).
- Keeping both would need an invoker wrapper over a definer core in a schema PostgREST does not expose. Once the history facts were grouped, the board's admin call is 0.20 s against 0.12 s owner-run; most of the earlier 1.3 s was one correlated count re-running the policies' init-plans per worker, now a grouped join. Not worth a new schema and a second authorisation path.

## Consequences
- **Equivalence.** pgTAP 854 re-creates the old pool, wrapper, one-worker gate, `series_gate_for` and the hotfix's Radar under `_old_` names in the test transaction and compares, over a fixture reaching all thirteen gate codes, both waves, every booking state, the series gate, the 2 h gap at another venue and back-to-back at the same one, the term cap and the radius: list and escalation reads, every section × worker one at a time, a named list, `auto_assign_candidates()`, `auto_assign_worker_gate()`, and nine workers' Radar (rows, every column, order). It also pins `reliability = coalesce(staff_show_rate(), 90)` and hours_limit / rtw_expired exactly where `weekly_cap_would_breach()` says, so a later change to either helper fails it. Breaking the gap window or the wave's do-not-return test in the new pool fails 5–8 of its assertions. On the bench data, 80 list reads, 4,158 one-worker reads and 10 named reads matched the old pool row for row, and seven workers' Radar matched (one only up to the order of exact ties, which the new tie-breaker fixes).
- **The migrations check what they replace.** The pool's body is fingerprinted (md5 of 20261012140000's source) and the migration stops if it differs; Radar and the wrapper are rewritten by patterns that must each match once (docs/10 §3b).
- **Not fixed: Radar is still one pool read per candidate section, 0.5–1.7 s at this scale, well inside the 8 s limit but not the 300 ms hoped for.** A one-worker read costs ~4.4 ms when the worker reaches the RULE-20 check, ~3 ms of it the cap helpers (`weekly_cap_for`, `can_roster_staff`, `cap_term_state`, `weekly_cap`, `rota_guard_decide`) being parsed and planned again on every call because they are nested SQL functions with `SET search_path` (audit F3, the parallel RULE-20 work). A two-role worker's Radar is ~190 own-row reads plus ~170 RULE-17 reads; a new starter's about half that. When that work lands, expect roughly a halving; if Radar still needs to be faster, the next step is a pool that judges one worker against many sections in one call, which is a larger change to the one place gates are decided and is not done here.
- `packages/db/src/types.generated.ts` still shows `staff_open_shifts` with `p_staff` only until the types are regenerated after deploy; the Staff App's client is untyped (`staffDb`), so nothing breaks meanwhile.
- 804 names the new two-argument signature.
